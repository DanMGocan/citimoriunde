# Authentication, secrets and operations

The authenticated session is obtained server-side from Better Auth, not a submitted member ID. Passwords use the library's supported scrypt implementation. Verification is required, password resets revoke sessions, cookie sessions are database-backed without a shared cookie cache, and origin/body-size/rate guards protect the authentication boundary. Google uses the server authorization-code flow; user-supplied ID-token/scopes import is disabled, implicit linking is disabled, and explicit linking requires a fresh verified local session. Provider roles are never trusted. Raw token/profile endpoints and hard user deletion are not exposed by the route wrapper.

Successful browser auth JSON omits session bearer tokens, provider token keys, session IP addresses and user-agent strings. Session management displays opaque session identifiers; selected-session revocation resolves the corresponding token server-side only after verifying ownership. The supported server-only `auth.api` remains unchanged. Authenticator enrolment may return a secret-bearing setup URI/recovery codes only in the signed-in account's protected setup flow; these are intentionally not included in public/admin config projections or logs.

Provider/local avatar URLs are discarded. Application profiles/forum render only the allowed database icon identifier; no uploaded/custom Google/Gravatar image is a profile picture. Additional factor enrolment uses Better Auth's supported TOTP plugin with passwordless enrolment for genuine Google accounts. Because OAuth sign-ins are not challenged by this plugin by default, administrative domain actions also require a server-side session-bound TOTP step-up marker in production. A new/revoked session cannot inherit another session's marker. Administrator factor disable is blocked. Recovery requires a documented operator process and audit, never a hidden bypass URL.

The first administrator is not seeded. The configured owner email may create a real verified Google identity while public registration is disabled, but remains an ordinary member until verified onboarding/TOTP and the one-time local bootstrap command pass. This exception does not allow an unverified local signup or elevation based on an email string alone. Production public signup additionally requires eight real published policy slugs alongside protected reviewed configuration.

The initial legal/admin dependency is resolved by a protected local operator command, not by bypassing age, published terms or TOTP. `legal:export` creates eight clearly marked drafts in a new review directory. `legal:bootstrap` requires all reviewed files, actual operator/contact configuration, `LEGAL_REVIEWED=true` and explicit `--confirm-reviewed`; it refuses a still-marked draft or a prior administrator/publication. It appends published versions and file hashes transactionally, auditing a local operator attestation without inventing a legal reviewer. Review and real operator details remain external prerequisites. Later publication belongs to the authenticated audited admin workflow.

Secrets and environment variables are read only by the typed config module. It sends explicit non-secret projections to the browser/admin UI. Auth email jobs contain token links for delivery, are scrubbed when done, and expire/scrub after two hours even when SMTP fails. Worker logs short fixed errors and no payloads. These token-bearing jobs and auth records are sensitive database data; backups require the same access restrictions. Health and readiness expose status/blockers, never connection strings, SMTP credentials, OAuth secrets or tokens.

Compose binds preview HTTP to loopback, publishes no database port, sanitizes proxy IP headers, and runs web/worker without root/capabilities. Native development should bind to loopback or an operator-approved interface and should not trust public `X-Real-IP`. One durable worker claims with row locks/SKIP LOCKED, retries/backoff, stale-claim recovery and a heartbeat. SMTP delivery has at-least-once behavior: a worker crash after a successful SMTP accept but before the database acknowledgement may resend the same Message-ID. This is not an exactly-once delivery guarantee.

Object-level authorization, transactional loan ownership/state constraints, moderation evidence access auditing, image decoding/EXIF stripping, safe text/links, forum revisions and private-data projections belong to their respective domain modules and require actual integration/security tests. A source review or syntax check does not prove all security properties. Dependency installation/build, real external providers, network listeners, container startup and restore/load/browser checks must be recorded honestly in TEST_REPORT.md; unavailable sandbox capabilities remain blockers.

Before launch, separate maintenance/database-owner privilege from the application login where practical, protect filesystem/runtime logs, set real retention/processor/incident responsibilities, review CSP/consent script allowlists, and verify backup restore. The initial Compose database account owns its own database to support migrations; it is private and is not a public member identity. Keep optional scripts/providers disabled until their endpoints, configured identities and consent prerequisites are verified. Never use live ad requests or real private content in automated tests.

HTTP local registration validates explicit adult/terms booleans and available legal versions before account creation. A server-only creation-hook context distinguishes genuine new users from generic duplicate-email responses; only genuine new accounts receive the saved adult assertion and the terms/privacy/lending document IDs. Duplicate signup never changes an existing member. Internal `auth.api` calls are trusted server interfaces used by isolated library contract tests, not public HTTP endpoints. Google members complete policy/adult onboarding separately. These declarations are participant assertions, not age or identity verification.

Every HTML request receives a fresh server nonce in `src/proxy.ts`; the root layout and owned script loaders preserve that nonce. Client-supplied nonce headers are replaced. CSP uses `strict-dynamic`, disables objects/framing and blocks third-party frames/connections on private routes. Reviewed configured advertising/CMP routes permit HTTPS creative resources; AdSense's documented `unsafe-eval` requirement is limited to the reviewed integration path (and development). Consent checks still gate script/request creation. Documents must reload when moving across a loaded CMP/Google/private CSP boundary. These controls require the unrun real-browser checks; a pure CSP-string test cannot prove network silence. Sources: [Next.js nonce CSP](https://nextjs.org/docs/app/guides/content-security-policy), [AdSense CSP requirements](https://support.google.com/adsense/answer/16283098).

A moderation hold on a physical copy is separate from its lending state/owner visibility. A database check requires held copies to stay private, owner edits cannot clear the hold, and new acceptance cannot lend a held copy. Active loan history and real return confirmation remain possible. Copy/review edits invalidate advertising review status. Idempotent extension approval references a specific extension record; message retries must match their original conversation and body. These protections have authored PostgreSQL regressions, awaiting execution.

Approval never turns a private copy public. Releasing a hold preserves PRIVATE visibility until its current owner chooses publication, including after gifting. New loan requests/reservations also check approved canonical work metadata and an active library under locks. Physical lifecycle database checks require non-null lender confirmation actors, avoiding PostgreSQL's acceptance of UNKNOWN CHECK results. Review/reading writes resolve redirects under work locks to preserve them during merges. These constraints are implemented, with unrun database regressions.

Moderators use a scoped queue separate from the administrator dashboard. It returns bounded case metadata, pending photos and review responses without private-message snapshots, deployment settings or unrestricted member lists. Transaction-review moderation uses the historical loan library. Case evidence remains separately authorised/audited. Forum moves preserve their original library when destination is omitted; moving across cities/global scope requires both permissions.

SMTP requires TLS/certificate validation and complete configured credentials, with bounded phase timeouts and no plaintext fallback. Connection verification sends no email; launch readiness requires a distinct operator delivery attestation. Shutdown stops fresh claims, safely releases interrupted claims and completes existing deliveries. SMTP retries cannot guarantee exactly-once inbox delivery. Caddy access logging remains disabled, and its default error-log encoder removes complete request/response-header fields to avoid callback tokens, cookies and private URLs. Filter syntax was reviewed against [Caddy logging](https://caddyserver.com/docs/caddyfile/directives/log) and [global options](https://caddyserver.com/docs/caddyfile/options); actual Caddy validation remains blocked.
